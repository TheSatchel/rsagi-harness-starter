# 参赛队接入规范 v0.2.0

本版按“一份真实参赛 Harness 跑通”交付，不要求八队压测。算法、记忆、自修改和自组织是否符合比赛规则，由主办方人工审核；平台负责 API 与游戏运行的正确性和固定故障处置。

## 队伍需要提交什么

1. 完整 Harness 源码、依赖锁定文件和启动入口；提供一个启动命令，比赛中不临时下载依赖。
2. 按 `sdk/examples/submission.json` 声明接口版本、入口、主办方源码共享及赛后公开授权。
3. 说明自修改/自组织的位置、允许写入的运行数据及使用的提示模板，供主办方审核。无需队伍实现一套自动合规证明器。

比赛运行环境注入三项配置：`RSAGI_API_URL`、`RSAGI_TEAM_TOKEN`、`RSAGI_MATCH_ID`。队伍不接触供应商密钥、后台世界接口或主办方管理员凭据。

## 推荐怎么写

从 `sdk/examples/baseline.py` 开始。SDK 的 `run_harness()` 处理轮次状态与恢复；队伍在提交的 Harness 中组织模型推理与动态结构，不重复实现网络确认或世界读写。

```python
from rsagi_harness import CompetitionClient, run_harness

client = CompetitionClient.from_env()
run_harness(client)
```

仓库示例可直接 `python3 sdk/examples/baseline.py` 启动。自建项目应赛前安装并锁定相同版本的 SDK。当前 API/SDK 版本均为 `0.2.0`，版本不符时在动作提交前明确拒绝。

只保留比赛 ID、轮次、余额、操作 ID、观察/票据/修订引用等机械状态。世界信息仍由模型从玩家画面、F3 和游戏声音理解；禁 RAG、外部语义笔记和传统规划器的规则不变，其内容审核归主办方。

## 每一轮按服务端状态处理

| 状态 | Harness 应做的事 |
| --- | --- |
| `OPEN` | 选择积攒额度或预留一次调用；调用前扣额度 |
| `PENDING` | 用 `active_operation_id` 查询原操作，不再发起模型调用 |
| `DECIDED` | 取得原操作票据；已有修订不重复应用，然后提交 ready |
| `READY` | 等下一轮，不再次调用或提交 |
| `FINISHED` | 正常退出 |
| `ABORTED` | 停止并上报主办方，不自行重开、回滚或跳过 |

队伍用其他语言时，也必须实现这张状态表。不能只写“每轮调用一次模型”的无状态循环。

## 重试、断线与重新启动

SDK 遇到传输失败，默认最多重试两次，沿用完全相同的比赛标识、请求编号和请求体。收到明确的协议拒绝不会换参数试探；重试用尽会返回 `TransportUncertain`，不会自动开一个新模型操作。

Harness 控制进程重新启动后，可以使用同局凭据与锁定的 `RSAGI_MATCH_ID`，查询当前轮次继续已有操作。服务端在 round 中给出本队原操作引用；这不包含世界事实，也不需要本地存储模型记忆。已应用的配置与已 ready 的轮次不能重复执行。

每个非 session 请求都带 `X-RSAGI-Match`，服务器不一致时返回 `MATCH_MISMATCH`。控制器不得自动换入一个新比赛；新局由主办方明确发放新配置。

这里恢复的是 Harness/API 连接，**不包括 Minecraft 玩家断线、服务端重启或游戏世界回滚**。这类事件按主办方固定停赛规则处置；不要把“重启 Python 后能继续查询”当作世界可一致恢复。

## 比赛故障的固定处理

| 故障 | 固定处理 |
| --- | --- |
| HTTP 回包丢失 | 同编号重试或查询已有操作，不重复扣费/执行 |
| 模型超时、非法动作 | 主办方按预先公布规则结算 WAIT，已预留额度不返还 |
| 票据、轮次或比赛 ID 不匹配 | 拒绝请求，不修改游戏 |
| 主办方/供应商公共故障 | 全局停止，不把故障计成某队的新动作 |
| 已停赛后的迟到模型回复 | 不签发可执行票据，不恢复推进 |
| 模型/感知/执行能力未接好 | 明确拒绝，不能退回后台世界文字或冒充在线比赛 |

## 队伍自测与主办方验收

```sh
python3 sdk/examples/demo.py
python3 scripts/verify_harness_api.py
```

默认 demo 只有一份 Harness，完成十二轮、60 个模拟 tick、五次合成调用和一次配置修订。两客户端屏障是小型协议回归，可用 `python3 sdk/examples/demo.py --teams 2` 运行，不是八队压测要求。

主办方赛前清单：

1. 人工审核源码与运行中变化规则，锁定入口、依赖、代码版本及三个环境变量。
2. 在最终客户端、服务器、模型配置上跑通一份真实 Harness，实际检查第一人称/F3/声音、移动、挖掘、界面、合成、战斗、死亡处置和计分。
3. 检查正常完成、网络回包丢失、控制器重新启动、模型超时、非法动作和人工停赛，确认不会多扣费、多执行或擅自推进。
4. 封存试跑记录，比赛时只运行验收过的构建与配置。赛中故障按已公布处置处理，不临时修改协议。

当前仓库已提供协议层单 Harness 自测；真实图像/声音和完整游戏执行仍待接入，所以不能把上述 Mock 命令的成功当作第 2 项已经完成。
